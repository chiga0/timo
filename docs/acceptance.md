# Timo 首版纵向试点验收剧本

本文用于人工与自动化联合执行和记录验收，**不表示对应能力已经实现或通过**。未执行项一律记为 `NOT_RUN`；入口缺失记为 `BLOCKED` 并记录具体缺口。

首版端到端基准场景：用户通过 Timo 独立 Web 工作台（或 CLI）委派一个 SSE 断连修复任务，涉及前后端两个仓库，总助理在 Standing Policy 范围内静默放行常规只读与 PR 权限，Timo 自主管理多仓 worktree 与本地 Capability MCP Gateway，分别提交两个 MR 并以 0-Token 跟踪所需 CI，独立执行组合行为验收，明确禁止生产发布。执行过程中支持一键下钻查看真实执行器的「实时运行流」、由两级 Watchdog 兜底卡死/走偏，并支持通过不可变目录快照与 Fencing Token 安全切换执行器。

## 1. 验收前准备与证据分类

- 锁定 Timo 提交、外部执行器（Codex / OpenCode / Pi / T3）、模型和配置版本；记录机器、网络位置与操作入口。不得用“最新版”代替实际版本。
- 准备两个试验仓库与 MR/CI 平台，分别记录仓库身份、目标分支、锁定的精确 `baseSha` 与当前执行代次；准备可复现的 SSE 故障与已知正确行为。
- 准备用户 `StandingPolicy`（区分总助理可自主批复范围与必须请示人的红线）、测试只读日志身份与试验 MR 身份；仅记录账号别名与范围，绝不记录凭据值。
- 固定验收管线（`VerificationPlan`）、总预算和软/硬期限。预算覆盖多轮修复、交接、Watchdog 会诊与独立验收；不可取得费用单列为未知，不得记零。

### 证据分类

| 标记 | 含义 | 不能据此声称 |
| --- | --- | --- |
| `FIXTURE` | 模拟执行器、模拟平台或人为故障注入，输入与预期固定 | 已验证真实模型、真实账号或平台集成 |
| `REAL` | 使用记录版本的真实执行器、仓库、账号与平台 | 已覆盖其他模型、平台或生产环境 |
| `MIXED` | 部分真实、部分模拟，逐项列清替代位置 | 整条链均为实机通过 |

单项结论采用 `PASS / FAIL / UNKNOWN / BLOCKED / NOT_RUN`。故障反例正确拦截错误候选、旧代次越权或盲目重试时，该剧本结论为 `PASS`，但对应业务任务本身仍按真实状态记为失败、等待或未知。

## 2. S01：正常交付，双仓两 MR、0-Token 等 CI、组合验收、不发布

建议输入：

> 排查前后端 SSE 断连，修复后分别提交两个 MR，等指定 CI 通过再通知我。只允许读取约定的预发日志，不要发布，不要进入生产交互式 Shell。

1. 提交任务，检查控制面事件账本记录的 `BriefRevision`、`GrantRevision`、禁止发布护栏、预算与期限；Web 主对话返回接单卡，不因常规权限反复追问。
2. 核对自主 `WorkspaceManager` 为两仓创建了独立 `g1` worktree 且精确命中锁定 `baseSha`（缺分支时显式失败而不静默 fallback），原工作目录及其他任务目录未被写入。
3. 核对执行器通过本地 Capability MCP Gateway 获取获准只读日志，且 `tools/list` 中不存在未授权的生产发布工具。
4. 独立验收引擎在干净环境中验证前后端组合重连行为（漏事件、重复事件与恢复时间均符合约定），而非仅看两仓各自单测。
5. 提交两个 MR，记录稳定操作 ID、平台 MR ID、目标分支与精确 `head SHA`。进入 `waiting_external_ci` 后由 Outbox 0-Token 跟踪 CI，确认等待期间无持续大模型调用。
6. 查看最终交付汇报：根因、两仓精确版本、MR/CI 链接、可展开原文的独立证据以及“生产未发布”核对记录。

通过条件：两份 MR、对应 CI、组合验收均绑定最终候选组合且全部通过；全过程遵守授权护栏。任何单次 `Run completed` 或单仓 CI 绿灯均不得单独宣告任务完成。

## 3. S02：不可变目录快照交接与代次 Fencing Token（原范围不变）

本剧本仍要求 S01 的两个 MR 与 CI，不含需求改口。

1. 第一执行器（如 Codex）在 `g1` 完成部分修改（含未提交改动和未跟踪文件）或已创建第一个 MR 后，要求改用第二执行器（如 Pi 或 OpenCode）继续同一 Task。
2. 核对系统执行不可变交接流程：发出中断 → **立即作废 `g1` 的网关 Fencing Token** → 将 `g1` 的 `git diff` 与未跟踪文件冻结迁移到全新 `g2` worktree → 生成标准化 **Handoff Capsule**。
3. 新执行器在 `g2` 接续：核对已有改动和未跟踪文件完整保留、已创建的第一个 MR 未重复提交、原 CI 仍按原 ID 跟踪、禁止发布护栏与全树预算未重置。
4. **关键反例（旧写者残留）**：人为保留一个在 `g1` 目录持续写文件、并继续使用 `g1` Fencing Token 调用本地 MCP 网关尝试创建 MR 的后台进程。
   - 预期：① `g1` 的垃圾写入物理上完全无法污染 `g2`；② 网关对 `g1` 的所有外部写请求一律返回 `GENERATION_REVOKED`；③ 旧代次迟到回执不得覆盖当前 `g2` 候选或宣布任务通过。

## 4. S03：用户改口与多任务防串台（Amendment Diff 确认卡）

场景前提：同时存在至少 2 个活跃任务；目标任务已创建第一个 MR，第二个 MR 尚未准入。

1. 在主对话中输入自然语言改口指令（如“停止后续前端修改和新增 MR，仅保留已经创建的后端 MR，不要关闭或发布”）。
2. 核对主对话**不直接静默覆盖**，而是先弹出明确标注 `Task ID`、原约定 vs 新约定 Diff 及外部影响的 **Amendment Diff 确认卡**，防止多任务并发时指代串台。
3. 用户点击确认生效后，检查 `BriefRevision` 与 `GrantRevision` 递增、旧版本可追溯，且第二个 MR 创建权限立即失效。
4. 释放一条旧版本派发或迟到结果，确认无法触发新写入，也不能将原双 MR 目标标为已完成。
5. **竞态分支**：若第二个 MR 请求在改口前已发往平台，系统须先查平台真实效果并如实披露；证据不足保留 `effect_unknown`，绝不未经授权关闭已建 MR 伪造“只保留一个”。

## 5. S04：回执丢失、进程强杀与离线恢复（`effect_unknown` 对账）

优先用 `FIXTURE` 稳定复现窗口，再在可清理试验仓库做 `REAL` 验证，分别记录。

1. 在平台已创建 MR、Timo 尚未保存回执的窗口切断网络或 `SIGKILL` 强杀 `timo serve`。
2. 重启服务后，核对进程清理残留锁/socket 正常启动，且自动通过 `task_events` / `outbox_jobs` 补查在途任务（不丢失在途状态，也不立即盲目重发创建请求）。
3. 平台可查到匹配 MR 时，自动关联原回执并恢复 CI 跟踪；平台无法确认且无有效幂等保证时，停留在 `waiting(effect_unknown)`，前端展示专用对账卡（含未确认操作 ID、最后核验时间与风险提示），仅提供“重新向平台核查”与“人工确认”动作。
4. 在等 CI 期间关闭服务或休眠，恢复后按 `afterSeq` 补齐前端 SSE 事件，重复投递同一 CI 变更事件不产生重复任务、重复修复或重复通知卡。

## 6. S05：错误候选、陈旧证据与环境污染不得误收

准备 1 份合法候选及至少 2 份错误候选（一份遗漏断连恢复，一份伪造日志行号或伪造“测试通过”文件）。

1. 合法候选通过声明式验收管线，确保验收器不因实现风格不同误杀合法方案。
2. 分别提交错误候选，确认独立验收在隔离环境中重算/实测后拒收；流畅的总结文案与候选自带的结果文件不得覆盖真实失败。
3. 验收通过后修改任一仓库候选（产生新 SHA），核对旧组合验证证据自动失效（`stale`），必须重跑受影响检查项才能再次接纳。
4. 验证含中文/非 ASCII 字符的冻结输入字节在落盘与回读前后 SHA-256 完全一致；验证旧环境缓存/脏文件不会被新验收环境继承。

## 7. S06：总助理分级委派授权、工具裁剪与凭据隔离

使用测试身份与受控端点逐项验证：

| 测试条件 | 预期行为 |
| --- | --- |
| **Tier 0/1 常规请求**（如预发只读日志、开发仓提 PR） | 在用户 `StandingPolicy` 范围内，总助理自主静默批复 `GrantRevision` 并写入审计流，**不向主对话弹审批打扰人**。 |
| **工具可见性裁剪** | 禁止生产发布的任务，网关 `tools/list` 不向 Worker 暴露发布工具，Worker 不会因误调无权工具陷入反复报错循环。 |
| **执行中途合法提权（Tier 2 红线）** | Worker 申请查看生产只读日志等红线权限时，任务原地挂起（`Pause & Resume`），保留 worktree 与进度并推送 1 张红线审批卡；用户批准后原地续跑，拒绝则按原范围收口，不判失败重跑。 |
| **凭据过期或环境不匹配** | 区分认证失效、权限不足与网络故障，保留恢复位置并在“环境与授权”面板显式告警；绝不自动换管理员身份，其他独立任务不受阻塞。 |
| **凭据物理隔离** | Worker 进程环境变量与工作目录中不可见真实业务 Token；越权绕过网关的尝试受目标平台权限或隔离边界阻止，不只靠提示词约束。 |

## 8. S07：人的净投入、收敛性与同预算效率

由目标用户使用自然语言在独立 Timo Web 中完成 S01，并与“用户直接使用单个原生执行器”做同任务、同必须项、同总预算对照：

- 分别记录正确交付率、端到端耗时、全部尝试成本（未知单列）、人工净阅读/操作/审阅分钟数、必要打断次数与重复提问次数。
- 预算耗尽时确认停止接纳新工作，但仍保留已有最佳候选与证据说明，不通过删减必须项伪造完成。
- 合法长耗时 CI 等待期间不产生无意义重规划或持续模型调用。

## 9. S08：两级 Watchdog、实时运行流透视与注意力防火墙

1. **一级 0-Token Watchdog**：
   - 注入“执行器进程静默无输出超阈值”、“连续 3 次相同失败报错死循环”、“改动文件数超出范围预警”三类故障；
   - 验证在 0 模型消耗前提下，Watchdog 按设定阈值准确发出 `WATCHDOG_SIGNAL`。
2. **二级总助理会诊与纠偏**：
   - 收到死循环或走偏信号后，总助理唤醒会诊：能自动恢复时直接向 Worker 注入纠偏指令（`steer`）或切换执行器接力；无法自动收敛时向主对话推送 1 条结构化 `TASK_BLOCKED_FINAL` 简报（含卡点、已尝试动作与建议选项）。
3. **实时运行流下钻与人工纠偏**：
   - 在任务运行期间，验证主对话保持安静；点击右侧检查器切至「实时运行流（Live）」，可实时看到归一化工具调用、终端输出与文件 Diff；输入一条人工纠偏指令可准确送达当前 Run 并记入审计。
4. **注意力防火墙防刷屏反例**：
   - 启动一个包含 2 个仓库、10+ 次工具调用、2 次单测重试与 1 次总助理自动批复权限的任务；
   - 核对主对话与「待你决定」收件箱中**零过程日志、零子任务刷屏**；同一任务若多次更新待决信息，Inbox 仅原地 Upsert 保留 1 条卡片。

## 10. 证据记录模板

每个剧本独立留存一份记录，正文引用稳定证据位置与摘要，严禁附带凭据值：

```text
剧本编号 / 执行日期：
证据类型：FIXTURE | REAL | MIXED（逐项说明替代位置）
执行者 / 独立验收者 / 目标用户：
Timo 提交 / 执行器与模型版本 / StandingPolicy 版本：
机器、网络位置、实际入口（Web / CLI）：
Task ID / Execution 代次 / Fencing Token 摘要 / Run ID：
BriefRevision / GrantRevision（含总助理自动批复与人工红线审批记录）：
各仓 baseSha / 候选 SHA / worktree 路径 / MR 与 CI 关联：
VerificationPlan 版本与检查环境：
预算、期限、实报成本及计量缺失：

步骤 | 预期 | 实际观察 | 原始证据位置或摘要 | PASS/FAIL/UNKNOWN/BLOCKED/NOT_RUN

业务结果：已完成 / 未完成 / 效果未知
剧本结论：
残留外部效果与所需处置：
人工净投入、打断次数与注意力防火墙评估：
缺陷、复测候选与未验证范围：
```
